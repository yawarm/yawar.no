Can an AI agent read door paperwork?

High-security door projects come with a lot of documentation. I built a LangGraph agent that takes instructions in plain language and does the reading.

2025 · 7 min read

Rapp Bomek makes high-security doors, such as fire doors, burglar resistant doors and soundproof doors. Each project comes with a lot of documentation, and someone has to read it, find the requirements that matter and write them down in a structured way. This takes time, and it is easy to make mistakes.

As an AI engineer at Astar Consulting, I built a command-line agent for them with LangGraph and LangChain. You give it an instruction in plain language, and it does the steps on the project documentation itself. This replaced manual reading with automatic extraction and structuring.

One prompt or an agent

The simplest approach would be to put all the documents into a language model and ask the question. For real project documentation this does not work very well. The documents are long, and even large context windows become expensive and less reliable when they are full. Real tasks also have several steps, like finding the right documents, reading the right sections, extracting the details, checking them and putting them together. Finally, a long answer in plain text is hard to check.

An agent lets the model decide what to do next, using tools, in a loop, until the task is done.

Agents as graphs

LangGraph models an agent as a state machine. There is a shared state \(S\), which can contain the instruction, the documents found so far and the extracted results. Each node is a function that reads the state and returns an update:

$$S_{t+1} = S_t \oplus f_{v_t}(S_t),$$

where \(v_t\) is the node that runs in step \(t\) and \(\oplus\) merges the update into the state. The edges decide which node runs next. Some edges are fixed, for example that extraction is always followed by validation, and some are conditional and depend on the state or on the model:

$$v_{t+1} = \operatorname{route}(v_t, S_{t+1}).$$

The graph can have cycles, so the agent can plan, act, look at the result and decide again. This is the usual reason-and-act loop, but with an explicit structure around it, which makes it possible to control where the model is free to choose.

A minimal example

A minimal sketch of the pattern (not the production code) looks like this:

from typing import TypedDict
from langgraph.graph import StateGraph, END

class State(TypedDict):
    instruction: str
    documents: list[str]
    findings: list[dict]
    done: bool

graph = StateGraph(State)
graph.add_node("plan", plan)          # LLM decides what to look for
graph.add_node("search", search)      # find relevant documents and sections
graph.add_node("extract", extract)    # LLM pulls out structured fields
graph.add_node("check", check)        # validate against the schema and sources

graph.set_entry_point("plan")
graph.add_edge("plan", "search")
graph.add_edge("search", "extract")
graph.add_edge("extract", "check")
graph.add_conditional_edges("check", lambda s: END if s["done"] else "plan")

agent = graph.compile()
agent.invoke({"instruction": "...", "documents": [], "findings": [], "done": False})

Structured output

In a system like this, I think the most important choice is to let the model fill in schemas, and not write free text. If every extracted item has to be a door with typed fields and a reference to where it was found, the output can be validated automatically, for example for missing fields or values that are not possible. If the validation fails, the agent can go back and look again, and a person can check any value against its source quickly.

Untick a field, as if the model did not find it. The validator catches it and sends the agent back to look again, so a guess is not passed on to a person.

This turns an open-ended generation problem into something closer to filling in a form, which is much easier to get right and to test.

A command line

The interface is a command line. You describe a task in your own words and get structured results back, and running a task again with a slightly different instruction is just one more line.

Some things I learned

It worked best to give the model freedom only where it was needed, with fixed edges for the steps that should always happen and conditional edges for the actual decisions. Structured output with validation caught more errors than changing the prompts. The goal was to replace the reading and not the judgement, so people check the results and do not have to produce them.
