An agent that reads door paperwork

High-security door projects come with a lot of documentation. I built a LangGraph agent that takes instructions in plain language and does the reading.

2025 · 7 min read

Rapp Bomek makes high-security doors: fire-rated, burglar-resistant, soundproof, often all at once. Every project comes with a pile of documentation, and someone has to read it, find the requirements that matter and turn them into structured information. It's slow, repetitive and easy to get wrong.

As an AI engineer at Astar Consulting, I built an agentic command-line system for them with LangGraph and LangChain. You give it an instruction in plain language, and it carries out the multi-step work on the project documentation itself, replacing manual review with automated extraction and structuring.

Why not just one big prompt?

The naive approach is to paste everything into a language model and ask. That breaks down quickly for real project documentation:

  • It doesn't fit. Project documents are long, and even large context windows get expensive and less reliable when filled to the brim.
  • One shot is fragile. Real tasks have several steps: find the right documents, read the right sections, extract the details, check them, put them together.
  • You can't check it. A wall of text from a model is hard to verify. Structured output, step by step, is something a person can audit.

An agent solves this by letting the model decide what to do next, using tools, in a loop, until the task is done.

Agents as graphs

LangGraph models an agent as a state machine. There's a shared state \(S\), for example the instruction, the documents found so far and the extracted results. Each node is a function that reads the state and returns an update:

$$S_{t+1} = S_t \oplus f_{v_t}(S_t),$$

where \(v_t\) is the node running at step \(t\) and \(\oplus\) merges the update into the state. Edges decide which node runs next. Some are fixed ("after extracting, always validate"), and some are conditional, chosen from the state or by the model itself ("is the answer complete, or do we need to search again?"):

$$v_{t+1} = \operatorname{route}(v_t, S_{t+1}).$$

Cycles are allowed, which is the whole point: plan, act, look at the result, and decide again. That's the classic reason–act loop, but with explicit structure around it, so you control where the model has freedom and where it doesn't.

The pattern, in code

A minimal sketch of the pattern (not the production code) looks like this:

from typing import TypedDict
from langgraph.graph import StateGraph, END

class State(TypedDict):
    instruction: str
    documents: list[str]
    findings: list[dict]
    done: bool

graph = StateGraph(State)
graph.add_node("plan", plan)          # LLM decides what to look for
graph.add_node("search", search)      # find relevant documents and sections
graph.add_node("extract", extract)    # LLM pulls out structured fields
graph.add_node("check", check)        # validate against the schema and sources

graph.set_entry_point("plan")
graph.add_edge("plan", "search")
graph.add_edge("search", "extract")
graph.add_edge("extract", "check")
graph.add_conditional_edges("check", lambda s: END if s["done"] else "plan")

agent = graph.compile()
agent.invoke({"instruction": "...", "documents": [], "findings": [], "done": False})

Structured output

In a system like this, I think the most important choice is to have the model fill in schemas instead of writing prose. If every extracted item has to be, say, a door with a set of typed fields and a reference back to where it was found, then:

  • the output can be validated automatically (missing fields, impossible values),
  • a failed validation can send the agent back for another look instead of silently passing on a guess,
  • and a person can check any value against its source in seconds.

Try: untick a field, as if the model failed to find it. Notice: the validator catches it and sends the agent back to look again, instead of passing a guess on to a person.

Mathematically, you're turning an open-ended generation problem into something closer to filling in a form, which is a much easier problem to get right and to test.

A command line

The interface is a command line rather than a web app. You describe a task in your own words and get structured results back, and rerunning a task with a slightly different instruction is just one more line.

What I learned

  • Give the model freedom only where you need it. Fixed edges for the steps that should always happen, conditional edges for real decisions.
  • Schemas beat prompts. Structured output with validation catches more errors than any amount of prompt tuning.
  • Keep the human in the loop where it's cheap. The goal is to replace the reading, not the judgement: people check results instead of producing them.
