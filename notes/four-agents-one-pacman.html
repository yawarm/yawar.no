What happens when four AI agents work as a team?

I gave four Claude agents separate roles and a shared folder, and let them build two small games together while a script passed messages between them.

2026 · 4 min read

I wanted to see what happens if several Claude Code agents get separate jobs, like in a small team, and have to coordinate by themselves. The setup was four agents and a few shell scripts.

The team

  • The lead plans the work, writes the task list and briefs the others, but never writes code itself.
  • Coder 1 and Coder 2 are full-stack developers, and the work is split between them by which files they own.
  • The reviewer reviews every plan and every piece of code, and has to approve before anyone starts building. It does not write code either.

The rules for the team are in a shared CLAUDE.md. The most important rule is that the coders have to post a plan and wait for the reviewer to approve it before they write any code.

tmux, files and a watcher

Each agent runs in its own tmux window. A start script creates the session, opens one window for each role and one for a watcher, and starts each agent with its role:

tmux new-session -d -s team -n "lead" -c "$DIR"
tmux send-keys -t team:lead "bash $DIR/launchers/lead.sh" Enter
tmux new-window -t team -n "coder1" -c "$DIR"
tmux send-keys -t team:coder1 "bash $DIR/launchers/coder1.sh" Enter
# ... coder2, reviewer, and the watcher

The agents never talk to each other directly. They write to plain files, with tasks.md for the task list and one file per role in messages/. A small bash loop checks when the files were last modified every three seconds, and when something changes it types a message into the right terminal:

while true; do
  sleep 3
  NEW_TASKS=$(stat -f %m "$DIR/tasks.md")
  if [ "$NEW_TASKS" != "$LAST_TASKS" ]; then
    tmux send-keys -t team:coder1 "tasks.md was updated. Check it and messages/lead.md for your assignments." Enter
    tmux send-keys -t team:coder2 "tasks.md was updated. Check it and messages/lead.md for your assignments." Enter
    tmux send-keys -t team:reviewer "tasks.md was updated. Check it and messages/lead.md for context." Enter
    LAST_TASKS="$NEW_TASKS"
  fi
  # same idea for lead.md, coder1.md, coder2.md and reviewer.md
done

This is a simple solution without any framework or message queue. A side effect is that all the messages are markdown files that I could read afterwards.

First round: Snake

The first task was a Snake game with only Coder 1. From the message files, the timeline was:

TimeWhat happened
23:50Coder 1 posts a plan. The reviewer raises 5 issues, and one of them is marked as MUST FIX (how many key presses are queued, so that fast input cannot turn the snake back into itself). The plan is conditionally approved.
23:55The implementation is done.
23:58The code review approves it, with some minor suggestions.
afterA second review finds a bug. Moving into the square the tail is just leaving was counted as hitting itself.
00:05Coder 1 fixes the bug.
00:10Final approval.

It took about twenty minutes from the plan to a reviewed game of around 500 lines, and the review found one real bug.

Second round: a maze game with two coders

The second round needed both coders to work in parallel. The lead started by writing an API contract in tasks.md before anyone began. It described what the maze data looks like, what a character object contains and which file exports what, and it gave each coder their own files:

FileOwnerLines
maze.jsCoder 2183
entities.jsCoder 2582
game.js + index.htmlCoder 1757 + page

Both coders posted plans that looked fine on their own, but the reviewer did not approve them:

NOT APPROVED — resolve contract gaps first. Both plans are solid individually but have critical integration mismatches.

The problems were in how the parts fit together. The plans did not agree on who ends the "frightened" mode after a power pellet, or on what happens to a character after it has been eaten. After the contract was updated, the plans were approved and the coders worked in parallel. Coder 1 still needed an integration fix later to match the entity API, and then a round of fixes from the review.

Some things I learned

Most of the problems were at the boundaries between files, so writing down the interface before any coding started, and having someone check the plans against it, caught them early. The review also found a real bug in the Snake game, which would otherwise have been shipped.

The agents did not always stay in their roles. Loading the roles with the --agent flag did not stop them from doing other things, while a single line with --append-system-prompt that spelled out the role ("You NEVER write code") worked much better. The lead also tended to show its plan in its own chat, where the others could not see it, so its launcher needed an explicit instruction to write tasks.md with the Write tool.

On the practical side, opening new tmux windows that run a command directly was unreliable, while typing into existing windows with send-keys worked every time. Splitting the work by file, and not by layer, also kept the two coders from editing the same file.

Overall it was more like managing a fast and slightly forgetful team than using a tool, and clear interfaces and file ownership mattered as much as they would with people.
