Four AI agents, one tmux session

I gave a team of Claude agents separate jobs, a shared folder and a watcher script, and asked them to build a game together.

2026 · 4 min read

I wanted to see what happens if several Claude Code agents get separate jobs, the way a small team works, and have to coordinate on their own. The setup was four agents and a few shell scripts.

The team

  • Lead: plans the work, writes the task list and briefs the others. Never writes code.
  • Coder 1 and Coder 2: full-stack generalists, split by which files they own, not by frontend/backend.
  • Reviewer: reviews every plan and every piece of code, asks the annoying questions, and has to approve before anyone builds. Never writes code either.

The team rules live in a shared CLAUDE.md. One rule matters more than the rest: coders post a plan and wait for the reviewer's approval before they write any code.

tmux, files and a watcher

Each agent runs in its own tmux window. A start script creates the session, opens one window per role plus one for a watcher, and launches each agent with its role:

tmux new-session -d -s team -n "lead" -c "$DIR"
tmux send-keys -t team:lead "bash $DIR/launchers/lead.sh" Enter
tmux new-window -t team -n "coder1" -c "$DIR"
tmux send-keys -t team:coder1 "bash $DIR/launchers/coder1.sh" Enter
# ... coder2, reviewer, and the watcher

The agents never talk to each other directly. They communicate through plain files: tasks.md for the task list, and one inbox per role in messages/. The glue is a small bash loop that checks file modification times every three seconds and literally types a nudge into the right terminal when something changes:

while true; do
  sleep 3
  NEW_TASKS=$(stat -f %m "$DIR/tasks.md")
  if [ "$NEW_TASKS" != "$LAST_TASKS" ]; then
    tmux send-keys -t team:coder1 "tasks.md was updated. Check it and messages/lead.md for your assignments." Enter
    tmux send-keys -t team:coder2 "tasks.md was updated. Check it and messages/lead.md for your assignments." Enter
    tmux send-keys -t team:reviewer "tasks.md was updated. Check it and messages/lead.md for context." Enter
    LAST_TASKS="$NEW_TASKS"
  fi
  # same idea for lead.md, coder1.md, coder2.md and reviewer.md
done

It's crude: no framework and no message queue, just files and keystrokes. A side effect is that every message is a markdown file I can read afterwards.

Round 1: Snake

The warm-up was a Snake game, with Coder 1 alone. The timeline from the message files:

TimeWhat happened
23:50Coder 1 posts a plan. The reviewer raises 5 issues, one marked MUST FIX (how deep the input queue is, so fast key presses can't reverse the snake into itself). Verdict: conditionally approved.
23:55Implementation done.
23:58Code review: approved, a few minor suggestions.
afterA second review pass finds a real bug: a false positive in tail self-collision. Moving into the square the tail is just leaving was counted as a crash.
00:05Coder 1 fixes it.
00:10Final sign-off.

About twenty minutes from plan to a reviewed, playable game of roughly 500 lines, including one real bug caught in review.

Round 2: a maze game with two coders

The second round needed both coders working in parallel. The lead started by writing an API contract into tasks.md before anyone started. What the maze data looks like, what a character object has, which file exports what, and strict file ownership:

FileOwnerLines
maze.jsCoder 2183
entities.jsCoder 2582
game.js + index.htmlCoder 1757 + page

Both coders posted plans that were fine on their own, and the reviewer rejected them anyway:

NOT APPROVED — resolve contract gaps first. Both plans are solid individually but have critical integration mismatches.

The gaps were the kind of thing that breaks integration in human teams too: who is responsible for ending the "frightened" mode after a power pellet, and what happens to a character after it's been eaten. Once the contract was tightened, the plans were approved and both coders built in parallel. Even so, Coder 1 later needed an "integration fix" to align with the entity API, followed by a round of review fixes.

What I learned

  • Contracts first. The integration problems were all at the boundaries between files. Writing the interface down before coding, and having someone check plans against it, caught them before they turned into bugs.
  • Review catches real bugs. The tail-collision bug would have shipped without a second pass.
  • Roles drift unless you pin them. Loading roles with Claude Code's --agent flag didn't reliably stop agents from wandering outside their job. A single-line --append-system-prompt with the role spelled out ("You NEVER write code…") held much better.
  • Say "write it to a file". The lead happily displayed its plan in its own chat, where nobody else could see it. Its launcher needed an explicit "You MUST use the Write tool to create tasks.md… If you don't write them, nobody works."
  • Simple plumbing wins. Starting new tmux windows that run a command directly was flaky; typing into existing windows with send-keys was reliable.
  • Own files, not layers. Two coders editing the same file is a merge conflict waiting to happen. File ownership kept them out of each other's way.

Working with it felt more like managing a fast, slightly forgetful team than using a tool. Clear interfaces and file ownership mattered as much as they do with people.
